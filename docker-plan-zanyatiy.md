# План занятий по Docker (для сисадмина)

Опорная инфраструктура: Proxmox-кластер, Zabbix, PostgreSQL — уже в опыте.
Логика плана: каждый шаг цепляется за то, что ты уже знаешь. Не абстрактные упражнения, а вещи, которые сразу лягут в резюме и в разговор на техническом интервью.

**Ориентир по срокам:** блоки 1–2 — неделя вечерами, блок 3 — выходные, блоки 4–5 — ещё пара недель по чуть-чуть. Итого месяц-полтора до честной строки в CV.

Отмечай `[x]` по мере прохождения.

---

## Блок 0. Подготовка (полвечера)

**Цель:** рабочее окружение, чтобы не спотыкаться на установке.

- [ ] Поставить Docker Engine на рабочую машину (Linux — из официального репозитория Docker, не из дистрибутивного `docker.io`; на Win/Mac — Docker Desktop).
- [ ] Добавить себя в группу `docker`, чтобы не писать `sudo` каждый раз: `sudo usermod -aG docker $USER` → перелогиниться.
- [ ] Проверить, что всё живо: `docker run hello-world`.
- [ ] Убедиться, что стоит Compose v2 как плагин: `docker compose version` (именно `docker compose`, а не `docker-compose`).

**Критерий готовности:** `hello-world` отработал без sudo, `docker compose version` показывает v2.x.

> ⚠️ Держи в голове: старые гайды в интернете сплошь на `docker-compose` (v1, снят с поддержки). Синтаксис почти тот же, но команда — `docker compose`.

## Блок 1. Основы Docker (2–3 вечера)

**Цель:** контейнеры/образы стали рутиной, а не магией. Свой Dockerfile с нуля.

### Занятие 1.1 — жизненный цикл контейнера

Никакого курса, только руки:

- [ ] `docker run -d --name web -p 8080:80 nginx` — подними nginx, открой `http://localhost:8080`.
- [ ] `docker ps` / `docker ps -a` — разберись, чем отличается вывод.
- [ ] `docker logs web` и `docker logs -f web` — посмотри логи, поймай их в реальном времени.
- [ ] `docker exec -it web bash` — зайди внутрь, посмотри `/etc/nginx/`, `ps aux`. Пойми, что контейнер — это процесс, а не «маленькая ВМ».
- [ ] `docker stop web` → `docker start web` → `docker rm -f web` — управление жизненным циклом.
- [ ] `docker images`, `docker rmi`, `docker pull` — разберись с локальным хранилищем образов.

**Критерий готовности:** можешь по памяти поднять контейнер с пробросом порта, зайти внутрь, посмотреть логи и всё за собой убрать.

### Занятие 1.2 — свой Dockerfile

Возьми свой Python-скрипт (или напиши на 10 строк — например, простой HTTP-эндпоинт «я жив»). Задача — упаковать его.

- [ ] Написать `Dockerfile`:
  ```dockerfile
  FROM python:3.12-slim
  WORKDIR /app
  COPY app.py .
  CMD ["python", "app.py"]
  ```
- [ ] `docker build -t my-app:0.1 .` — собрать образ.
- [ ] `docker run --rm my-app:0.1` — запустить.
- [ ] Осознанно поменять что-то в `app.py`, пересобрать и заметить, какие слои пересобираются, а какие берутся из кэша.
- [ ] Разобраться с `.dockerignore` (чтобы не тащить в образ `.git`, `__pycache__` и т.п.).

**Критерий готовности:** есть рабочий `Dockerfile`, который ты понимаешь построчно, и ты объяснишь, почему `COPY app.py` идёт после установки зависимостей (кэш слоёв).

### Занятие 1.3 — volumes и networks

Это то место, где у новичков «данные пропали после рестарта». Тебе как сисадмину важно понять сразу.

- [ ] `docker volume create data1`, примонтировать: `docker run -v data1:/data ...`, записать файл, убить контейнер, поднять заново — убедиться, что данные на месте.
- [ ] Разница между **named volume** (`data1:/data`) и **bind mount** (`/host/path:/data`) — когда что.
- [ ] `docker network create mynet`, поднять два контейнера в одной сети, пингануть один из другого **по имени контейнера** (встроенный DNS Docker). Это фундамент того, как контейнеры общаются.

**Критерий готовности:** объяснишь, где живут данные PostgreSQL-контейнера и как сделать, чтобы они пережили пересоздание контейнера.

## Блок 2. Docker Compose (2–3 вечера)

**Цель:** мультиконтейнерная связка через один YAML — ближе к реальным задачам, чем один контейнер.

### Занятие 2.1 — первый compose

- [ ] Переписать связку из блока 1 в `compose.yaml`.
- [ ] Освоить: `docker compose up -d`, `docker compose ps`, `docker compose logs -f`, `docker compose down`, `docker compose down -v` (с удалением томов).
- [ ] Понять, что Compose сам создаёт сеть для проекта — сервисы видят друг друга по имени сервиса.

### Занятие 2.2 — app + PostgreSQL (твоя территория)

Здесь подключаем то, что ты уже знаешь — Postgres.

- [ ] Собрать стек: приложение + база.
  ```yaml
  services:
    db:
      image: postgres:16
      environment:
        POSTGRES_PASSWORD: secret
        POSTGRES_DB: appdb
      volumes:
        - pgdata:/var/lib/postgresql/data
      healthcheck:
        test: ["CMD-SHELL", "pg_isready -U postgres"]
        interval: 5s
        timeout: 5s
        retries: 5

    app:
      build: ./app
      depends_on:
        db:
          condition: service_healthy
      environment:
        DATABASE_URL: postgresql://postgres:secret@db:5432/appdb
      ports:
        - "8000:8000"

  volumes:
    pgdata:
  ```
- [ ] Разобраться, почему `app` обращается к базе по хосту `db` (имя сервиса = DNS-имя).
- [ ] Понять связку `healthcheck` + `depends_on: condition: service_healthy` — почему без неё app стартует раньше, чем база готова принимать соединения. Это классические грабли, и знать их — уже уровень выше junior.
- [ ] Зайти в базу: `docker compose exec db psql -U postgres -d appdb`.

**Критерий готовности:** app поднимается, дожидается готовности базы, пишет/читает данные; данные переживают `down` (без `-v`) и `up`.

### Занятие 2.3 — nginx как reverse proxy

- [ ] Добавить сервис `nginx` перед `app`, пробросить наружу только 80-й порт nginx, а `app` убрать из `ports` (пусть общается только внутри сети).
- [ ] Написать простой `nginx.conf` с `proxy_pass` на `app:8000`, примонтировать через bind mount.

**Критерий готовности:** снаружи доступен только nginx; он проксирует на app; app — на базу. Ты нарисуешь эту схему на бумаге за минуту (это ровно то, что спросят на собесе).

## Блок 3. Docker-хост на Proxmox (выходные)

**Цель:** реальный опыт «виртуализация → контейнеризация» на инфраструктуре, которую ты понимаешь. Честный пункт в резюме.

### Занятие 3.1 — VM под Docker

- [ ] На Proxmox поднять **отдельную тестовую VM** (Debian/Ubuntu), не трогая продакшен.
- [ ] Установить Docker Engine из официального репозитория.
- [ ] Проверить `docker run hello-world` внутри VM.

> ⚠️ Ставь Docker именно в **VM**, а не в **LXC-контейнер** Proxmox. Docker-in-LXC технически возможен, но требует возни с nesting/keyctl/cgroups и периодически ломается на апдейтах ядра. Чистая VM — предсказуемо и в резюме звучит честнее. (Если захочешь — отдельным экспериментом можешь попробовать LXC-вариант и прочувствовать разницу, но основной стенд — VM.)

### Занятие 3.2 — перенос стека

- [ ] Скопировать `compose.yaml` из блока 2 на VM, поднять там весь стек.
- [ ] Настроить автозапуск: `restart: unless-stopped` в compose + убедиться, что стек поднимается после ребута VM.
- [ ] (Опц.) Снять snapshot VM в Proxmox до и после — почувствовать связку «снапшот виртуалки + версионированный compose».

**Критерий готовности:** на выделенной Proxmox-VM крутится твой compose-стек, переживает перезагрузку VM. В CV появляется: «тестовое развёртывание Docker на Proxmox VE».

## Блок 4. Pet-проект + интеграция с Zabbix (пара недель по чуть-чуть)

**Цель:** задеплоить что-то, чем реально пользуешься, и связать с уже работающим мониторингом. Конкретный артефакт на GitHub.

### Занятие 4.1 — мониторинг Docker через существующий Zabbix (главный тай-ин)

Это сильнее, чем ставить отдельный Portainer: ты подключаешь контейнеры к уже работающему стеку мониторинга, а не заводишь параллельный.

- [ ] Развернуть `zabbix-agent2` (можно контейнером) на Docker-хосте с доступом к Docker socket (`/var/run/docker.sock`).
- [ ] Включить встроенный **Docker-плагин** agent2 (метрики: список контейнеров, состояние, ресурсы).
- [ ] Навесить официальный шаблон Docker by Zabbix agent 2 на хост в твоём Zabbix.
- [ ] Убедиться, что прилетают данные: количество контейнеров, статусы, потребление.

**Критерий готовности:** в твоём существующем Zabbix виден Docker-хост с метриками по контейнерам. Связка «Docker → agent2 → существующий Zabbix» — отличная строка для резюме.

### Занятие 4.2 — Portainer как веб-морда (по желанию)

- [ ] Поднять Portainer CE контейнером, подключить к локальному Docker.
- [ ] Погонять управление контейнерами/образами/томами через веб — полезно как удобный инструмент на каждый день.

### Занятие 4.3 — оформить на GitHub

- [ ] Завести репозиторий, выложить `Dockerfile`, `compose.yaml`, `nginx.conf`, конфиги мониторинга.
- [ ] Написать внятный `README`: что за стек, как поднять, схема сервисов. README-качество тут важнее кода — по нему смотрят, умеешь ли ты документировать.
- [ ] Вынести секреты в `.env` (и добавить `.env` в `.gitignore`, а в репо положить `.env.example`).

**Критерий готовности:** публичный репозиторий, который не стыдно дать ссылкой на собеседовании; поднимается по инструкции из README на чистой машине.

## Блок 5. Простой CI/CD на GitHub Actions (пара вечеров)

**Цель:** пайплайн, который сам собирает образ при пуше. Закрывает формулировку «podstawy CI/CD» в вакансиях.

### Занятие 5.1 — build + push в GHCR

- [ ] Создать `.github/workflows/build.yml`: при пуше в `main` — checkout → build образа → push в **GitHub Container Registry (GHCR)**.
- [ ] Использовать `GITHUB_TOKEN` для авторизации в GHCR (уже привязан к репо — меньше секретов заводить руками, чем с Docker Hub, и нет лимитов на pull).
- [ ] Проставлять тег образа по короткому SHA коммита и/или `latest`.

**Критерий готовности:** пушнул в репо → через минуту в GHCR лежит свежесобранный образ с правильным тегом.

### Занятие 5.2 — довести до ума (опц.)

- [ ] Добавить кэш слоёв в Actions (ускоряет пересборку).
- [ ] (Продвинуто) Автодеплой: после успешной сборки по SSH зайти на Proxmox-VM и сделать `docker compose pull && docker compose up -d`. Это уже мини-CD, и на собесе это заметно выделяет.

**Критерий готовности:** понимаешь разницу CI (сборка) и CD (доставка) и можешь показать хотя бы CI-часть работающей.

## Блок 6. Docker Swarm — мост к оркестрации (опционально)

**Цель:** мягкий переходный шаг к оркестрации, если позже соберёшься в сторону Kubernetes/OKD. Те же концепции (сервисы, реплики, балансировка), но проще.

- [ ] `docker swarm init` на VM.
- [ ] Развернуть стек как сервис: `docker service create` / `docker stack deploy` из compose-файла.
- [ ] `docker service scale app=3` — прочувствовать реплики и встроенную балансировку.
- [ ] Понять разницу «контейнер» vs «сервис vs задача (task)» — это ровно тот словарь, что нужен для разговора про Kubernetes.

**Критерий готовности:** можешь объяснить на пальцах, что такое реплики и балансировка, и чем оркестратор отличается от одиночного Docker-хоста.

> ⚠️ **Чего не делать:** не гнаться за Kubernetes сразу — там резкий скачок сложности. В вакансиях его часто просят только «podstawowo». Сначала Docker должен стать рутиной; K8s через Minikube/kind — уже потом, отдельной темой.
